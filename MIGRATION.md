# Migrating to a new machine

Read `AGENTS.md` first for what the project is. This file is only about getting it running elsewhere.

---

## 0. The thing to understand before you start

**The zip does not contain the product.** It contains the source, the local keys, and the history.
Three things that matter live elsewhere and cannot be zipped:

| What | Where it lives | Why it matters |
|---|---|---|
| **The live ledger** — every player balance, every settled round | Fly volume `bulls_data` at `/data` | `engine/data/ledger.db` in the repo is a **stale Aug-6 copy**. It is not the live book |
| **The mainnet vault key** (`VAULT_SECRET_KEY`) | Fly secrets | Not on disk anywhere. Fly will not show it back to you |
| **The Helius RPC key, and ~20 tuning vars** | Fly secrets | Same — write-only by design |

So a laptop migration moves your ability to *develop*. Your ability to *operate* depends on keeping
access to the Fly account. **Before wiping the old laptop, confirm you can log into Fly from the new
one.** Everything else here is recoverable; that is not.

```bash
fly auth login
fly apps list          # you should see bulls-arena-engine
fly secrets list --app bulls-arena-engine
```

If that works on the new machine, you have lost nothing.

## 1. What is in the zip

Everything except things that rebuild themselves:

**Included** — source, `.git` (full history, both branches), `web/`, `programs/`, `scripts/`, all
documentation, and **all secrets on disk**:

```
.devnet/fork-payer.json              devnet payer keypair
.devnet/program-keypair.json         devnet program keypair
engine/.vault-keypair.json           DEVNET vault (4iDuXiq…GAFy)
engine/data/bot-wallets.json         devnet bot wallets
engine/data/bot-wallets-mainnet.json ⚠ MAINNET bot wallets — REAL MONEY
engine/data/bot-pool.json            pool addresses
engine/data/ledger.db                stale local ledger copy (NOT the live book)
```

**Excluded** — regenerated by a command:

| Excluded | Size | Rebuild with |
|---|---|---|
| `engine/node_modules/` | 76 MB | `npm install` |
| `target/` | 917 MB | `cargo-build-sbf` |
| `.toolchain/` | 640 MB | see §4 |
| `.xwin-cache/` | 1.1 GB | `xwin splat` |

That is ~2.7 GB of rebuildable artefacts left out, against a few MB of irreplaceable material kept.

### Handling the zip

It contains **private keys that control real funds**. Treat it accordingly:

- Move it on physical media or a direct machine-to-machine transfer.
- Do not email it, do not put it in cloud storage, do not put it in a shared folder.
- Delete it from both machines once the new one is verified working.
- If it is ever exposed, the mainnet bot wallets must be drained to new keys immediately.

## 2. Restore

```bash
# 1. unzip wherever you keep projects
cd ~/projects
unzip bulls-arena-migration.zip
cd bulls-arena

# 2. confirm the history came across — you should see both branches
git log --oneline -3
git branch -a
git status                     # should be clean

# 3. dependencies
cd engine && npm install && cd ..

# 4. tests — everything must pass before you trust anything else
node --experimental-strip-types --test engine/src/tests/*.test.ts
```

Expect **~361 passing, 0 failing**. If anything fails, stop and read it; the suite is the fastest
signal that the restore is intact.

## 3. Running the live product

The engine only runs against mainnet with the Fly secrets, which stay on Fly. To develop locally:

```bash
cd engine
cp .env.example .env           # then fill in a devnet RPC
npm run dev                    # or: node --experimental-strip-types src/server.ts
```

To deploy the live product (from `main`, and only deliberately):

```bash
fly deploy . --config engine/fly.toml --dockerfile engine/Dockerfile --ha=false --app bulls-arena-engine
```

**Note:** a deploy has twice returned `401 Unauthorized` on the *post-deploy status update* while the
release itself landed fine. Verify with `curl https://bulls-arena-engine.fly.dev/health` before
assuming it failed and redeploying. The Fly token looks close to expiring — refresh it early.

## 4. The Solana toolchain (only needed for the ER fork)

This was the hardest part of the original setup, and none of it is obvious. If the new machine has
**Visual Studio Build Tools with the Windows SDK**, skip all of it — everything just works.

Without VS (which is where the old machine was):

```
Problem: cargo-build-sbf pins an msvc-HOSTED toolchain, so host build scripts must link as MSVC —
         but there is no MSVC and no admin rights to install one.
```

The chain that worked:

```bash
# 1. a host linker, user-scope, no admin
winget install -e --id BrechtSanders.WinLibs.POSIX.UCRT.LLVM --scope user

# 2. xwin — needs a host linker to build, which is why step 1 comes first
rustup default stable-x86_64-pc-windows-gnu
cargo install --locked xwin
rustup default stable-x86_64-pc-windows-msvc

# 3. fetch the MSVC CRT + Windows SDK IMPORT LIBRARIES (headers are not needed —
#    rustc links, it does not compile C, and the header splat fails without symlink privilege)
xwin --accept-license --arch x86_64 splat --output .toolchain/xwin

# 4. lld-link stands in for the absent MSVC link.exe
mkdir -p .toolchain/shim
cp "$LOCALAPPDATA/Microsoft/WinGet/Packages/BrechtSanders.WinLibs.POSIX.UCRT.LLVM_*/mingw64/bin/lld-link.exe" .toolchain/shim/link.exe

# 5. Solana CLI (its installer needs admin only for a final symlink — the binaries work without it)
#    binaries end up in ~/.local/share/solana/install/releases/<ver>/solana-release/bin
```

Then to build, with **`LIB` set via the environment, not rustflags** — `cargo-build-sbf` sets
`RUSTFLAGS` itself and env wins over `.cargo/config.toml`; `lld-link` reads `LIB` exactly as MSVC's
linker does:

```bash
export PATH="<mingw>/bin:<solana>/bin:$PATH"
export LIB="$PWD/.toolchain/xwin/crt/lib/x86_64;$PWD/.toolchain/xwin/sdk/lib/um/x86_64;$PWD/.toolchain/xwin/sdk/lib/ucrt/x86_64"
cargo-build-sbf --manifest-path programs/bulls-arena/Cargo.toml
```

`.cargo/config.toml` (already in the repo) sets `linker = "lld-link"`.

## 5. Devnet, for the ER fork

```bash
git checkout magicblock-er-migration
solana config set --url https://api.devnet.solana.com

# the payer keypair came in the zip; check it still has SOL
solana balance $(solana-keygen pubkey .devnet/fork-payer.json) --url https://api.devnet.solana.com
```

If it is empty, the faucet is usually rate-limited. **The reliable trick: closing an old deployed
program refunds its rent**, which is normally more than a redeploy costs.

```bash
solana program close <OLD_PROGRAM_ID> --keypair .devnet/fork-payer.json --bypass-warning --url https://api.devnet.solana.com
```

Then:

```bash
cd engine
node scripts/er-roundtrip.mjs      # full lifecycle: delegate → ER → commit → undelegate
node scripts/er-cu-bench.mjs       # compute measurements
```

## 6. First things to check on the new machine

Work down this list; each one either passes or tells you what is missing.

1. `git log --oneline -3` — history intact, both branches present
2. `node --experimental-strip-types --test engine/src/tests/*.test.ts` — ~361 pass
3. `fly apps list` — **the one that cannot be recovered from the zip**
4. `curl https://bulls-arena-engine.fly.dev/health` — live product still serving
5. `curl https://bulls-arena-engine.fly.dev/solvency` — books still reconcile
6. `ls engine/data/bot-wallets-mainnet.json` — the real-money keys arrived

If 3 fails, stop and sort out Fly access before doing anything else.
